# Forensic Admission State Semantics V1

## Purpose

This document is a permanent architectural invariant for every successor Bot/AI working on `Project_Brain_AI`.

The database admission chain is **one ordered forensic state machine**, not multiple independent forensic systems.

## Canonical chain

```text
DB_EXISTENCE
    -> DB_BINDING
    -> DB_TLS_ADMISSION
    -> DB_ROUND_TRIP
    -> PROMOTION
```

Each gate is an independent proof obligation.

## Non-inheritance rule

A PASS at gate N is **only a prerequisite** for attempting gate N+1.

It does not grant, imply, inherit, predict, or approximate PASS at any deeper gate.

Therefore:

```text
DB_EXISTS = PASS
    DOES NOT IMPLY
DB_BINDING = PASS

DB_BINDING = PASS
    DOES NOT IMPLY
DB_TLS_ADMISSION = PASS

DB_TLS_ADMISSION = PASS
    DOES NOT IMPLY
DB_ROUND_TRIP = PASS

DB_ROUND_TRIP = PASS
    DOES NOT IMPLY
PROMOTION = PASS
```

## Strict reachability

Evaluation is left-to-right and monotonic in **reachability**, not in trust.

The first failed/unknown gate stops the chain:

```text
PASS -> PASS -> FAIL
                  |
                  +--> all deeper gates = UNREACHED
```

A deeper raw boolean flag must never be surfaced as `PASS` when the gate was never reached.

`UNREACHED` is not `PASS`, not `FAIL`, and not `NOT_PROVEN`. It means the proof obligation was not legitimately attempted because an earlier prerequisite failed.

## Failure persistence

A failed gate must produce an immutable evidence record containing at minimum:

- gate
- status = `FAIL`
- reason code
- event timestamp
- evidence identifier/hash
- runtime anchor identity
- immutable = true

A later retry may produce a new event with a new result, but must never erase, mutate, or overwrite the earlier failure record.

Historical failure remains forensic truth even if a later attempt succeeds.

## Round-trip semantics

A durable database proof must not be reduced to a single optimistic echo.

The stronger target is temporal validation using fresh values/nonces:

```text
WRITE nonce A
    -> READ nonce A
WRITE nonce B
    -> READ nonce B
    -> verify A != B
    -> verify both reads equal their writes
    -> hash compact evidence of A+B
```

The proof must use a real durable PostgreSQL connection over an admitted TLS mode.

No credential, password, full connection string, source dataset, or secret-derived material may appear in logs, GitHub, or action receipts.

If the implementation cannot prove that the read came from the intended durable path, the round-trip gate remains `DENY`/`NOT_PROVEN` according to the state-machine semantics.

## Environment proof

Local environment and Render environment are different trust domains.

A local successful database test cannot be promoted to Render evidence.

Render evidence must be generated by the exact deployed runtime anchor.

```text
LOCAL PASS != RENDER PASS
DOCUMENTATION HEAD != RUNTIME ANCHOR
DATABASE EXISTS != SERVICE AUTHORIZATION
```

## Promotion rule

Promotion requires independent proof of every preceding gate in order and a real compact durable write/read verification with hash match.

No shortcut, inferred trust, cached result, synthetic database response, or copied local receipt is valid promotion evidence.

## OOM invariant

All proof operations must preserve the Render Free memory boundary:

- hard platform boundary: 512 MiB
- project guard: 320 MiB
- no bulk dataset loading for Brain governance checks
- compact evidence envelopes only

If a forensic proof requires large memory, it must be isolated outside the Brain runtime rather than weakening the guard.
