# Forensic Admission Chain — Mandatory Successor Contract

## Core invariant

`PROVISIONED != EXECUTED != CAPTURED != RECORDED != VALIDATED != PROMOTED`

A later state may never be inferred from an earlier state. Every promotion requires evidence generated by the corresponding gate.

## Database admission chain — ONE FORENSIC FSM

```text
DB_EXISTS
   |
   v
DB_BINDING
   |
   v
DB_TLS_ADMISSION
   |
   v
DB_ROUND_TRIP
   |
   v
PROMOTION
```

These are not independent Forensic systems. They are ordered evidence gates inside one admission FSM.

Meaning:

- `DB_EXISTS`: the PostgreSQL resource exists and is observable. This proves the room exists and grants zero access authority.
- `DB_BINDING`: the service runtime has an explicit binding named `DATABASE_URL` through the approved secret boundary. This proves the service has a key, not that the key is safe.
- `DB_TLS_ADMISSION`: the binding is PostgreSQL and uses an accepted TLS mode (`require`, `verify-ca`, or `verify-full`).
- `DB_ROUND_TRIP`: the service actually writes one compact metadata envelope, reads it back, and verifies the expected SHA-256 relationship. No source data, credentials, or bulk datasets are permitted in this envelope.
- `PROMOTION`: only after the corresponding round-trip evidence is captured and validated may durable DB use be admitted.

## Non-inheritance rule

```text
DB_EXISTS=PASS
    does NOT imply
DB_BINDING=PASS

DB_BINDING=PASS
    does NOT imply
DB_TLS_ADMISSION=PASS

DB_TLS_ADMISSION=PASS
    does NOT imply
DB_ROUND_TRIP=PASS

DB_ROUND_TRIP=PASS
    is the prerequisite for
PROMOTION=PASS
```

PASS is local to the exact gate that produced it. It is a prerequisite for the next gate, never a PASS inheritance mechanism.

## Failure semantics

A failure is forensic evidence, not permission to silently repair the evidence path.

Examples:

```text
DNS_FAIL       -> round_trip = NOT_CAPTURED, reason = DNS_FAIL
TLS_FAIL       -> round_trip = NOT_CAPTURED, reason = TLS_FAIL
TIMEOUT        -> round_trip = NOT_CAPTURED, reason = TIMEOUT
BLOCKED        -> round_trip = NOT_CAPTURED, reason = BLOCKED
NOT_BOUND      -> binding = NOT_BOUND, promotion = DENY
```

Do not retry solely to manufacture a PASS. Any retry must itself be an explicitly logged execution with its own receipt identity.

## Governed Wait — ACTIVE_HOLD / NO-OP

`WAIT_EXTERNAL_EVENT` is a valid governed state. It is not `IDLE`, `STUCK`, or `ERROR`.

Canonical hold snapshot:

```text
FOUNDATION = FROZEN
STATE = WAIT_EXTERNAL_EVENT
MODE = ACTIVE_HOLD
SEALED = TRUE
ACTION_SPACE = 0
REQUIRED_ACTION = NO-OP
TRANSITION_AUTHORITY = LOCKED
```

The rule is:

```text
NO EVIDENCE
   -> NO TRANSITION
      -> NO ACTION
         -> NO-OP
```

No-op is therefore a valid forensic action at the current frontier.

## `next_action` law

`next_action` is a DAG pointer only. It is not execution authority, authorization, or permission.

When the FSM is `WAIT_EXTERNAL_EVENT`, the pointer is frozen. A successor Bot must never execute the pointed node merely because the pointer exists.

Transition authority is zero until a genuine external event produces a Fresh Runtime Receipt with evidence > 0.

```text
Fresh Runtime Receipt?
    |
    +-- NO  -> ACTIVE_HOLD / NO-OP
    |
    +-- YES -> verify receipt integrity
                 |
                 +-- FAIL -> DENY / NO-OP
                 |
                 +-- PASS -> evaluate exact FSM transition
```

## External event law

An external event cannot be manufactured by the Bot.

Forbidden substitutes include fabricated webhook receipts, fake GitHub workflow dispatch evidence, synthetic deployment receipts, simulated database receipts, or any internally generated object treated as a real external event.

## Runtime-2 closure

Foundation closure requires an independent fresh runtime observation:

```text
Runtime-2
  -> EXECUTED
  -> CAPTURED
  -> RECORDED
  -> COMPARED
  -> STOP
```

If Runtime-2 fails, the failure itself is recorded and Foundation remains open. No staircase, Layer 1 promotion, or successor shortcut is permitted.

## Successor protocol

A successor Bot must:

1. Read `state/current_state.json`.
2. Read `state/next_action.json`.
3. Read the latest action log.
4. Read this contract.
5. Determine the exact FSM state.
6. Determine whether a Fresh Runtime Receipt exists.
7. If state is `WAIT_EXTERNAL_EVENT` and no fresh receipt exists, perform `NO-OP`.
8. Never interpret `next_action` as execution authority.
9. Never convert `UNKNOWN`, `NOT_PROVEN`, or `DENY` into PASS by inference.
10. Append an action log before changing canonical state.
11. Preserve previous forensic history as immutable evidence.

## OOM invariant

Render Free has a hard 512 MB boundary. Brain runtime retains a 320 MiB guard. Durable work must remain compact and must never load bulk datasets into the Brain process.

## Canonical principle

```text
EVIDENCE -> STATE -> ACTION

NOT:

DESIRE -> ACTION -> FIND EVIDENCE
```

The second pattern is explicitly prohibited.

## Seal

This document is normative. The chat window is not the source of truth. Repository state, contracts, action logs, and Fresh Runtime Receipts are authoritative.

Until a genuine external event supplies fresh runtime evidence, the foundation remains frozen, the current action frontier remains `ACTIVE_HOLD / NO-OP`, promotion remains `DENY`, Layer 1 remains `LOCKED`, and the staircase remains `LOCKED`.
