## Key decision — CANONICAL

The database admission model is **ONE Forensic FSM**, not multiple independent forensic systems.

There is one state machine and one evidence ledger. The apparent “multiple forensic states” are local gate results inside the same admission chain.

Sequential gates:

```text
DB_EXISTENCE
   -> DB_BINDING
   -> SECRET_RESOLUTION
   -> DB_TLS_ADMISSION
   -> NETWORK_ORIGIN_PROOF
   -> DB_ROUND_TRIP
   -> PROMOTION
```

### Non-inheritance law

```text
PASS(G_n)  !=>  PASS(G_n+1)
```

A PASS is **local evidence for its own gate only**. It never becomes authority for the next gate by inheritance or inference.

Examples:

```text
DB_EXISTS = PASS
    !=> DB_BINDING = PASS

DB_BINDING = PASS
    !=> SECRET_RESOLUTION = PASS

DB_TLS_ADMISSION = PASS
    !=> DB_ROUND_TRIP = PASS

DB_ROUND_TRIP = PASS
    => only then may PROMOTION be considered,
       subject to all other gates being PASS.
```

This distinction is mandatory because resource existence, authorization, secret resolution, transport admission, network-origin proof, and real persistence are different forensic facts.

## External trigger rule

For transitions requiring a real external event, Brain/Bot/chat cannot fabricate the event or evidence. Admissible GitHub workflow origins are:

- real manual workflow dispatch;
- real source push/commit event;
- real authorized external API dispatch.

Fresh runner execution identity and receipt must be observable before the FSM may consume the evidence.

`WAIT_EXTERNAL_EVENT` is valid and must not be converted to PASS by inference.

### Retry law

```text
RETRY = NEW FORENSIC EVENT
```

A retry may append a new receipt/event but may never overwrite, delete, or mutate historical receipts.

## Protected-room analogy

```text
corridor key -> room key -> inner latch -> doorbell/external event -> admission
```

Correct keys do not manufacture the inner release.

The analogy is a security model, not an assertion that the runtime has physical rooms or keys.
