# BRAIN-N018 — Safe Render DB Linkage Gate

## Action

Inspected the live `xsmb-quant` Render service and existing Render Postgres authority. The service is Docker-based, free plan, one instance, Singapore, with auto-deploy from `main`.

The previous foundation gate could crash the web process if database persistence was enabled while linkage/credentials were absent or invalid. That violates availability and OOM-safe fail-closed design.

## Change

`foundation_gate.py` was hardened so persistence and evidence-roundtrip failures become explicit `DENY`/`PENDING` evidence instead of terminating the service.

A new `/verification/durability` surface exposes metadata-only durability state. It never exposes `DATABASE_URL`.

## Current boundary

```text
Render service
  -> bounded verifier
  -> safe durability probe
  -> metadata only
```

The database authority remains the existing Postgres instance. No competing database was created.

## Important status

`DATABASE_URL` linkage is not yet runtime-proven. Therefore:

- durability = PENDING/DENY;
- promotion = DENY;
- Layer 1 = LOCKED;
- staircase = LOCKED.

## Why this is correct

A missing secret/linkage must not crash the service and must never be replaced by a guessed credential or filesystem fallback.

## Next action

BRAIN-N019: after the current auto-deploy becomes live, inspect runtime durability state and only then enable the actual round-trip if the database linkage is present. Capture explicit PASS or DENY evidence.
