# BRAIN-N039 — Formal Security Chain Gate

## Finding

The foundation had individual security components, but no single ordered composition boundary. This created a successor-Bot risk: a future implementation could call the components in the wrong order or treat a sensor result as authorization.

## Implemented

`core/security_chain.py` now defines the explicit order:

```text
OBSERVE
  ↓
EXTERNAL ROOM AUTHORIZATION
  ↓
REQUEST INNER RELEASE
  ↓
ASSERT INNER RELEASE
  ↓
ENTRY
```

The composition is fail-closed.

## Invariants

```text
sensor_signal != capability
capability != entry_release
correct_key != inner_release
warning != authorization
```

For a protected room, correct external credentials can reach `RINGING`, but cannot produce `ENTRY_RELEASED` without an authorized occupant release.

Wrong key/capability or wrong directional layer edge returns DENY before the inner latch is activated.

## Tests

`tests/test_security_chain.py` covers:

- valid external authorization still requires inner release;
- invalid credentials do not activate the latch;
- wrong directional edge is denied before latch request;
- sensor light does not become authority;
- authorized occupant is the final release step.

## Important correction for future implementations

Do not let a generic `authorized=True` sensor flag become an access token. The sensor is observational telemetry. Authorization must come from the room-lock verifier.
