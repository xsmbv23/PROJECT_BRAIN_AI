# BRAIN-N041 — Two-Key Access Path + Protected Room

## Architectural correction

The access model is explicitly **two-key**, not one-key:

```text
CORRIDOR KEY
    +
ROOM KEY
    ↓
REQUEST ENTRY
```

The corridor key proves the visitor may traverse that corridor. The room key proves the visitor may request access to the destination room.

These keys are separate objects and fingerprints. A valid room key cannot substitute for a corridor key, and a valid corridor key cannot substitute for a room key.

## Protected owner/special room

For a protected room, the two keys do **not** open the door directly:

```text
corridor key ✓
room key ✓
    ↓
DOORBELL / ENTRY REQUEST
    ↓
INNER LATCH = SECURED
    ↓
AUTHORIZED OCCUPANT INSIDE
    ↓
RELEASE FROM INSIDE
    ↓
ENTRY
```

The external party is therefore authorized to **request**, not to force entry.

## Implemented

`core/access_path.py`

- `CorridorKey`
- `RoomKey`
- `AccessPathPolicy`
- `verify_access_path()`

For protected rooms, the function stops at `DOORBELL_RUNG_WAITING_FOR_INSIDE_RELEASE`.

`tests/test_access_path.py` verifies:

- corridor key required;
- room key required;
- both keys required for ordinary room entry;
- protected room only rings after both keys pass;
- protected room cannot bypass inner latch.

## Security invariants

```text
corridor_key != room_key
room_key != inner_release
sensor != authorization
request != entry
external_authorized != inner_release
```

## Successor-Bot instruction

Never collapse corridor key, room key, and inner-release capability into one master credential. Each is a distinct security boundary with its own lock, audit event and failure state.

## OOM boundary
